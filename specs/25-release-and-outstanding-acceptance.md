## 4. Release 阻擋處理與同產物驗收

### 4.1 官方候選資格流程

以下流程留待後續開發，不是產品執行時自動下載／試版或重試：

1. **固定基準與相依鏈。** 從直接 PackageReference、當次 assets／deps 及發布檔案確認命中組件的 package ID、精確版本、目標資產與傳遞來源。歷史指出 Google.Apis.Auth，仍須重新核對，不以 item=000009 推定新清單是同檔。掃描公開診斷仍不列 path／offset／內容；維護者只在本機查必要的非機密套件 metadata。
2. **查官方固定來源。** 以官方套件 metadata、release notes 與對應固定 tag／commit 建立候選清單，記查核日期、來源與完整版本。正式來源缺失、不相容、仍命中及未實測分開；主分支、PR 或版本較新不構成資格。不得將 DLL 中的起始標記直接定性為真私鑰或已證明無害。
3. **限定相依變更。** 優先採能解決問題且相容的官方直接依賴修正版；只有官方相容範圍及解析證據支持時，才可精確固定傳遞依賴。若同時有多個合格版本，先選同一 major 的最低足夠正式修正版；只有無同 major 合格版本且既有 API／框架相容時才評估下一 major。來源不足則停止，不提供虛構版本。不可使用自行重建、修改或來源不明的套件。
4. **隔離重現。** 每個候選使用獨立來源副本、明確套件來源與精確解析記錄；下載／restore 屬開發前置，和之後離線回歸分開。保留原基準，不改使用者 SDK／快取內容或正式專案全域選版來湊通過。確認候選在 net10.0、現有 API、用途／容量／取消／認證政策下可建置且不新增重試或額外外送。
5. **取得全產物證據。** 依第 4.2 節完成乾淨與增量發布。候選單檔沒有命中仍不足；若其他檔命中、結構不符或掃描 incomplete，該候選不合格。掃描器及其完整規則不得變更。
6. **驗受影響功能後採用。** 使用正式 runtime factory＋假 HTTP 的既有模型／工具／容量／敏感／用量／委派等離線回歸及必要原生回歸，再依第 7 節取得相依變更影響的真服務證據。Google 相依變更至少重驗兩 Gemini profile；MCP 套件若未變仍須保留 Learn 未結門檻。選定版本與無合格候選的結論都必須可追溯。

目前沒有在本份查證的新候選或採用版本；這是後續資格流程的明確起點。候選失敗只停止該次採用；可比較另一個已明列候選，但不得自動重跑同一失敗命令或改規則。若沒有合格版本，記「官方相依候選受阻」，維持完整掃描與 Release 啟動禁令，不進行同產物 help／互動／分發。

### 4.2 發布、結構、掃描與啟動順序

沿用第 22 份的來源副本與離線 fixture，不複製舊 bin／obj、私人資料或 .git。完成必要依賴準備後，乾淨來源第一次發布及保留其當次建置輸出的第二次增量發布，使用兩個不同的新目錄。每次依序檢查：

1. publish 退出 0；CLI 為 framework-dependent、非單檔 DLL，輸出根無 CLI 自身 apphost。
2. 根四檔 `AIAgent.Cli.dll`、`AIAgent.Cli.deps.json`、`AIAgent.Cli.runtimeconfig.json`、`appsettings.json` 均為非空、非連結普通檔。
3. `ProcessHost/` 下 apphost `AIAgent.ProcessHost` 及其 `.dll`、`.deps.json`、`.runtimeconfig.json` 四件套同樣有效；apphost 可執行，四件套 SHA-256 對應當次 Release 建置輸出。最低八檔不代表總檔數固定。
4. 原儲存庫的既定 scanner 掃描完整輸出，包含相依 DLL、PDB、隱藏與非 UTF-8 普通檔；只有退出 0／passed 才能繼續。
5. 從該輸出執行 `--help`，須退出 0、零互動／認證／模型請求。隨後才可執行同產物的原生、真人及服務案例。

後續命令模板如下；`/example/` 均須換成實際位置。每段獨立判斷成功後才執行下一段，不當成無條件連續腳本：

```sh
dotnet publish src/AIAgent.Cli/AIAgent.Cli.csproj -c Release --no-restore --no-self-contained -p:UseAppHost=false -o "/example/new publish directory"
```

完成上述唯讀結構／權限／雜湊檢查後：

```sh
python3 -B "/example/original-repository/scripts/check_sensitive_content.py" artifacts --path "/example/new publish directory"
```

僅 scan 退出 0 後：

```sh
dotnet "/example/new publish directory/AIAgent.Cli.dll" --help
```

scan 退出 1 為完整觀察且有命中，退出 2 為未完整／參數等錯誤；兩者皆停止，不將 incomplete 降為 blocked，也不把「測試確認有停止」算成掃描成功。診斷只保留固定分類、item、規則、計數與退出碼，不傾印命中內容或原始 stderr。

### 4.3 後續測試修改邊界

優先延伸 test_release_publish.py 的 release_steps、結構檢查及可控停止案例；保留真 SDK 發布結果與 stop-boundary unittest 結果的分離。可增加同產物身分失效與候選 metadata 的離線案例，但不新增具有另一套規則的發布掃描器。掃描回歸保留六規則、所有編碼、跨塊與非零停止斷言，不將合成成功輸出替代真實 scan。

## 5. 原生缺口的 fixture 與驗收契約

### 5.1 執行層級、同步與安全收尾

每個案例標明入口：**產品受控服務**（真正 RunAsync、核准、探針、sandbox、ProcessHost 與固定 recipe）、**ProcessHost／Supervisor 直接案例**或**可控制替身**。後兩者補充失效分支，不替代產品正向入口與實際 sandbox。原生 fixture 不呼叫模型；MTP 仍由第 24 份准入。

fixture 使用已還原、`UseAppHost=false` 的合成小專案。長執行或後代行為由可信測試 helper／專案 target 觸發，準備與編譯留在開發者測試設定，不替產品增加自由命令。helper 只碰該次來源、bin／obj 或私人 tmp 允許範圍；敏感／越界拒絕測試只針對該次建立的合成 canary，禁止探讀真實憑證或 Keychain 資料。

測試 gate 只傳固定 ASCII 狀態與自有程序 metadata；可用既有 internal callback／snapshot provider 包裝真實觀測來確認「已納入監督」，不偽造成功快照。必須分開「helper 已建立子程序」「監督器已觀測」「已觸發故障」。產品路徑不能靠測試 hook 放寬政策或縮短 120 秒冒充完整期限。

每次建立獨立、受保護 fixture 根及測試擁有權紀錄。先啟動外部 watchdog，再啟動受測操作；真實 120 秒案例的外部硬截止為 150 秒，N06 身分上限案例為 60 秒，其餘非完整期限案例為 30 秒，均從 watchdog 就緒後啟動受測操作時起算。N06 的 60 秒包含最多 50 秒建立／觀測、產品既有最多 6 秒收尾、最多 2 秒觀察容差及 2 秒 guard 餘裕；未在建立／觀測期限取得 gate 即記失敗並開始自有程序收尾，不等到硬截止才取消。這些外部截止不修改產品期限；helper 自我到期不晚於相應截止。超時即失敗，記收尾情形。watchdog／finally 只能依該 fixture 的 PID＋開始時間等身分處理自有程序，不能按名稱或重用 PID 殺程序；此代清不證明產品 CleanupConfirmed。人工／環境硬故障使收尾不能確認時停止整批原生工作並保留阻擋，不繼續製造後代。

## 7. 真實服務操作與跨規格對照

### 7.1 授權、計費與停止

執行前另列當批目的地、profile、預定案例、產品預算與批次生成／外送次數上限，取得使用者明確授權。上限須在執行前填實；未填或未同意不呼叫。沿用產品唯一用量與額度，人工按次記錄；達批次上限、quota／認證／協定失敗或取消即停止該批，不透過切模型、重試或增加額度繼續。不宣稱固定 token 數等同實際帳單。

使用者自行在正式產品輸入真 Key，Agent 不從參數、環境、檔案、剪貼簿或工具取得。服務與真人記錄只保留安全分類、模型、數值、合成本機操作與結果；不攔截帶認證封包，不保存 raw SDK／HTTP／MCP、模型原生簽章或完整畫面。依序執行三 profile 可共用合成 fixture，但需各自結果及新的產品認證流程。

本節 profile 是目前產品值。後續開始前核對官方服務資訊及實際帳戶可用性；不可用就記實際分類，不自行替換名稱。真 Learn 不使用模型 Key；維持既有 connect、協定與每次外送核准。對認證切換案例，只用明確無功能假值觀察服務的實際拒絕，不修改或撤銷可用正式 Key 製造失敗。

### 8.3 人工分享與分發清單

承接 BUD-AC-048、049。由維護者逐項記結果，以下檢查不代表執行 Git 或對外動作的授權：

1. 核對實際 index 與 staged scanner 範圍；再檢查未暫存／未追蹤內容、範例與文件，不因 .gitignore 或掃描退出 0 跳過。
2. 核對擬分享的 README、PR／Issue、附件、截圖／錄影及報告，只保留安全內容。疑似真實認證洩漏先停止分享，由使用者撤銷／更換並檢查用量；歷史／副本處置另定，不自動改寫。
3. 核對候選來源、完整相依、許可資訊、實際平台聲明、必要檔／mode／雜湊及當次完整 scan、同產物 help 與必要功能證據，確保就是即將交付的內容。
4. 如另有封裝或簽章，須另次授權並對最終形式重查；scanner 不解析壓縮內部，不能把壓縮檔掃描失敗忽略。可在受保護目錄唯讀比對實際包內清單／解包內容與已驗目錄，再掃完整解包樹；記錄容器／內容雜湊、額外 metadata 及人工結果，仍不宣稱 scanner 理解容器一切。無合格最終形式檢查就不分發。
5. 無實際發布時記「指定產物檢查完成、未對外發布」。產物或擬分享材料變更後，重做受影響門檻；任何必要項未驗證／受阻就不宣稱可完整分發。

## 10. 證據狀態與安全紀錄模板

### 10.1 狀態語意

| 狀態 | 意義與是否計入通過 |
|---|---|
| 待執行 | 只有規格或準備，尚無當次操作；不計通過。 |
| 通過 | 該列所有必要斷言、指定入口／環境及收尾均有可核對證據。 |
| 失敗 | 有實際不符合契約的結果；保留原始次序與安全分類。 |
| 受阻 | 來源／相依／平台／外層環境／授權／quota 等前置不足，不能完成驗收；不計通過。 |
| 未觸發 | 有真實操作，但必要分支未發生；該分支未驗證，不計通過。 |
| 未執行 | 上游失敗／停止／未授權使後續沒執行；不計通過。 |
| 部分完成 | 同列有通過與未結子項；必須列子項，整列不計通過。 |
| 不適用 | 原契約明確排除該範圍，附來源及理由；不計通過，不能用來轉移本來必要的 MTP／平台／真人案例。 |

測試框架的 Skipped／Inconclusive 單列原始數字，映射成受阻／未執行等原因，不自動變成不適用。預期的能力拒絕、正確 Unconfirmed 或限制呈現可讓其**負向斷言**通過，仍不證明對應正向能力或全案例通過。重跑有新證據 ID，保留前次失敗與修正原因。

### 10.2 每批必要欄位

```text
證據 ID／日期／時區：
來源 commit／未提交檔案範圍／候選版本與官方固定來源：
層級／入口：文件、離線、產品原生、監督器直接、PTY、真人、服務、Release、人工分發
OS 產品版本／架構／檔案系統語意／終端機版本／IME／鍵盤設定：
實際 SDK／runtime／MTP 或 Git 及必要相依版本：
recipe／parser／sandbox 身分／外層執行條件：
產物識別：該次新目錄、來源／Configuration、必要檔與完整清單內容／mode 雜湊
服務 profile／官方目的地／授權範圍／批次生成與外送上限：
fixture 準備／離線前提／自有程序與 watchdog 收尾責任：
實際命令與退出碼，或真人逐步操作與觸發 gate：

產物是否變更／舊證據失效範圍／是否對外發布：
```

「完整清單雜湊」是維護者在合成／發布目錄對原始相對名稱、普通檔 bytes、mode 依固定排序形成的身分記錄，不增加 scanner 輸出或成功含義；記錄其形成方式，不能只 hash 八個必要檔便宣稱所有相依未變。產物路徑只作本機識別，對外可使用非機密證據 ID；掃描診斷本身仍不新增路徑／內容欄位。

命令只含非機密參數；禁止記 Key、認證標頭、完整應用指示、raw body、模型原生資料、敏感片段、原始 stderr／traceback 或完整終端機轉錄。對安全 canary／helper 僅記案例、雜湊是否一致、身分及結果數值，不將待掃資料複製成報告附件。原生 guard 代清與產品已確認收尾須各自填寫。
